# ZoKo and Gridz directory eligibility design

Researched 2026-10-03. This is a proposed architecture and policy interpretation, not provider approval, a selected business-model change, or a deployment. Current paid products and their release identities remain authoritative. No support message, submission, purchase, or hosting mutation was performed for this study.

## Finding and recommendation

There is no documented general route in the sources checked that combines universal-directory distribution with the complete existing pay-per-decision/pay-per-workload native-XEC marketplaces. The public plugin guidelines cover both skills and MCP plugins. They restrict digital-service commerce, including indirect commerce, and separately prohibit executing money or crypto transfers. Their explicit exception permits access to features already included in an existing paid subscription. These are directory rules; they do not establish that the independently documented Git-catalog distribution route is unavailable.

Keep the full marketplace products and pursue their independent catalog distribution. For a directory offering, the most plausible documented basis is genuine consumption of already included subscription services, with an explicit economic redesign and provider review of supplier fulfillment. Do not claim that this preserves spot-market purchasing inside the directory plugin. If agent-selected per-task XEC purchasing and seller trading inside the listed plugin are essential, the remaining requirement is an applicable published policy change or specific provider authorization for the actual flows. There is no such authorization in the available evidence.

## Current source boundaries

ZoKo 1.4.0 quotes a real independent seller and buys a typed judgment by debiting a custodial XEC ledger. Delivery credits the seller and marketplace commission. Native sellers must be actually active; an installed skill is not available inference. The operator supplies no continuously available inference. The directory account release is private, and the repository records no submitted public review.

Gridz's inspected 0.1.0 manifest and skill expose workload discovery, buy/sell orders and native-XEC escrow coordination using external signatures. Keeping private keys outside the plugin is an important security boundary, but does not itself remove digital commerce or crypto-transfer facilitation. The manifest admits only its registered SHA-256-chain executor; other compute classes require qualification. It would be inaccurate to market this release as an arbitrary GPU/CPU executor. The planned marketplace commission is quoted but its collection is not activated in that manifest.

These observations come from the source manifests and skills, not a new deployment or financial acceptance test. Gridz runtime and shared-host configuration were not changed.

## Options

| Route | What it preserves | What it does not establish |
| --- | --- | --- |
| Full paid plugins through independent Git catalogs | Agent-directed discovery, authorized quotes and purchases, independent sellers, native XEC and original settlement controls | Universal-directory presence, ranking, automatic installation or exemption from other applicable terms |
| Directory consumption of an existing subscription, with supplier procurement outside that plugin | Execution quality, authorized autonomous task submission, result retrieval and verification within purchased service limits | The original per-task buyer-to-seller spot market inside the directory; eligibility of this specific supplier model until reviewed |
| Directory integration with the user's own already provisioned endpoint or compute | Service execution within existing rights, with no new marketplace purchase | Marketplace sales, seller acquisition, or monetization merely from directory use |
| Unchanged marketplace plus specific provider authorization or future policy change | Potentially the entire original product | Current eligibility or approval; neither is evidenced |

A discovery-only directory advertisement for the full transactional plugin is not an established solution. The guidelines require standalone useful functionality and also address indirect sales. No automatic migration, checkout link, purchase-capable installer, or hidden external purchaser should be introduced as an alleged workaround.

## Conditional architecture for included services

Only implement this route after the owner selects a genuine subscription/service contract. An existing XEC deposit, general spending mandate or standing allowance is not evidence that service is already included in a subscription.

1. Authenticate the customer to an existing account. Server-issued entitlements bind the account, included service, period, permitted models or workload-meter identities, and usage limits. Directory credentials cannot create or upgrade those entitlements.
2. Let the directory plugin request an included typed decision or execute an included qualified workload. It can inspect available included capability, retrieve results and reconcile interrupted execution. A new request consumes service allowance; it cannot create a new priced customer purchase, debit spendable XEC or trigger customer overage billing.
3. Enforce this boundary on the server as well as in the shipped package. Separate credential audiences/scopes and handlers from bid/ask creation, paid quote acceptance, funding, withdrawal, escrow-spend coordination and wallet operations. Reject exhausted or wrong-service entitlements without a checkout flow. Do not rely on descriptive instructions or merely hidden UI buttons.
4. Preserve the existing engines: ZoKo schema validation, true seller/model identity, actual delivery deadlines and durable request recovery; Gridz exact workload/meter bindings, qualified executors, input protection, verification and execution recovery. Entitlement reservations must have durable identities and survive concurrent requests and restarts without duplicate consumption.
5. Supplier agreements and procurement must genuinely cover fulfillment of the included service. Describe any platform payments to independent suppliers, XEC settlement and per-request supplier costs truthfully to reviewers. A plugin endpoint that forwards each request into the customer's existing purchase API is not this redesign. Whether our supplier fulfillment constitutes prohibited indirect commerce remains a specific review question; architecture alone cannot certify it.
6. Keep full paid marketplace releases separately identified and accurately documented. Do not route directory credentials or skills into those purchase workflows. Quality for the same included service must remain equivalent across surfaces. Do not make a worse directory version or add a directory-specific surcharge.

This could preserve inference quality, model choice among included providers, workload execution and verification performance. It changes commercial semantics and financial risk: someone must contract for included capacity and bear supplier cost. The current marketplace-only operator-inference limit remains zero; this proposal does not authorize operator inference, supplier spending, customer billing or new resources.

## Autonomy and measurable performance

Both routes can respect a human's standing task authorization instead of repeatedly asking about covered actions. Financial authority remains specific to the paid route, with cumulative spend, fees, expiry, permitted counterparties and data limits. Included-service authority instead covers task, data, entitled capabilities and finite usage. Host or provider-required consent still applies.

Set latency, successful completion, correctness and recovery acceptance criteria before implementing an alternative. Compare identical real authorized tasks and equivalent providers against retained baseline receipts. Verify retries, process termination, exhaustion, parallel reservation, revocation, unavailable sellers, failed verification and credential isolation. Package tests, installed behavior, directory review, publication and customer adoption are separate evidence states. A proposed service design is not permission to dispatch new paid tests.

Gridz additionally needs useful workload qualification; changing its directory package does not activate discovery-only executors. ZoKo additionally needs independent authorized supply; changing metadata does not create sellers.

## Authoritative sources checked

- [Plugin guidelines](https://developers.openai.com/plugins/plugin-guidelines): directory scope, digital commerce, included subscriptions, transfers, quality, standalone usefulness and verification.
- [Checkout API reference](https://developers.openai.com/plugins/build/monetization): currently approved physical-goods commerce and limited marketplace payment-sheet beta. It does not document a digital-services or XEC exemption.
- [Plugin submission](https://developers.openai.com/plugins/deploy/submission): verification, review and publication are separate from packaging/private installation.
- [Plugin packaging](https://developers.openai.com/plugins/build/plugins): separate local/Git catalog distribution.
- [Commerce policies, updated September 29, 2026](https://openai.com/policies/commerce-policies/): shopping/merchant scope and a narrow software entitlement exception. This does not override the plugin-specific directory commerce restriction or establish that decisions/compute qualify as conventional software licenses.
- [Sign in with ChatGPT plan usage](https://developers.openai.com/siwc/token-sharing-open-source): the documented route covers open-source and locally hosted apps; paid or remotely hosted offerings are directed to an interest form. It is not evidence of permission to pool, transfer or commercially resell another user's subscription access. Our existing native session route exports no authentication and remains subject to each participant's account/platform rules.

The conclusions above are our reading of these sources. Neither product has a provider rejection or an approved digital-commerce exception evidenced here.
