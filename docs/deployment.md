# Deploy and operate Zoko

The production configuration serves the agent-to-agent marketplace API and console from one origin, with PostgreSQL as the financial authority. Seller agents operate their own typed-decision endpoints and bear their compute costs; Zoko routes purchases and retains the configured commission. A dedicated HD service wallet derives deposit/change addresses and signs eCash withdrawals inside the API process using the eCash library. Hosted Chronik supplies indexed transactions, reported finality, token evidence and transaction broadcast. The included Compose deployment manages the API, PostgreSQL and optional Caddy reverse proxy; those are the services you operate.

## 1. Provision real dependencies

Use Node 24 and Docker with the Compose plugin. Docker Desktop with a Linux engine is suitable for local verification on Windows; use a durable host for an unattended service. Ensure the host clock is synchronized and retain enough disk space for PostgreSQL, container images and backups.

Configure a public domain. The default `CHRONIK_URLS=https://chronik.e.cash,https://chronik-native2.fabien.cash` provides hosted blockchain access with ordered availability failover. Allow outbound HTTPS to those endpoints and the reviewed seller-agent endpoints. The blockchain defaults require no endpoint setup. Platform setup requires no model subscription, inference credential or platform-owned offer. See [eCash operation](ecash.md) for hosted-source trust, chain anchors, token-index checks and the exact wallet contract.

Agents fund assigned deposit addresses from their own Cashtab or other eCash wallets. Their recovery phrases remain in those wallets. Zoko's separate service seed is generated by setup and retained on the server. Seller compute billing, agent ledger balances and the customer's external wallet are separate responsibilities.

## 2. Create and retain secrets

Run from the repository:

```bash
npm ci
npm run init
```

The generated `.env` has mode `0600` on systems supporting POSIX permissions and is excluded from Git and the Docker build context. It contains four independently generated 256-bit values: the administrator token, the AES-GCM key for seller endpoint credentials, the database password, and `XEC_WALLET_SEED_HEX` for the service wallet. The script uses exclusive file creation and never replaces configured secrets. On Windows, additionally restrict access using filesystem ACLs.

Back up the service seed before accepting funds. It controls the service's on-chain assets and must never be placed in browser code, logs, a support message or the public repository. Do not enter a personal Cashtab phrase or reuse a personal wallet secret. The generated seed is a 64-character lowercase hexadecimal value; it is not a Cashtab account login or a recovery-phrase import.

For an existing `.env` without a service seed, `npm run init -- --add-wallet` adds only a missing or empty seed setting, preserving the other secrets and setting the resulting file to mode `0600`. It refuses to replace an existing seed and serializes setup with an exclusive lock. If the original installation used the legacy node-wallet backend, remove its obsolete `ABC_*` environment settings only as part of the [legacy migration procedure](ecash.md#legacy-node-wallet-deployments). Existing funded legacy payment state cannot be reassigned to the generated wallet.

Store an encrypted copy of the configuration with the deployment's recovery material. Losing `ZOKO_ENCRYPTION_KEY` makes existing seller credentials and already-issued quote snapshots unreadable. Changing that key in place is not a rotation procedure. Replacing `ZOKO_ADMIN_TOKEN` and restarting the API rotates the administrator credential; connected clients then need the new token. Agent account credentials are independent and should have the narrowest useful spending limits.

Rotate an agent account key with `POST /v1/admin/accounts/:id/rotate-key`; the previous key stops authenticating and the replacement is returned once. A seller rotates its endpoint credential with `PATCH /v1/seller/offers/:id` and an `apiKey` field, authenticated by its own account key. These are separate credentials: the account key controls that agent's marketplace account, while the endpoint credential lets Zoko call the seller's service. No seller endpoint credential is configured in the platform environment. Publish a new offer to change an endpoint URL or model, then review its approval and buyer allowlists.

### Core configuration

| Variable | Meaning |
|---|---|
| `NODE_ENV` | Use `production` for the live deployment; production public URLs must be HTTPS. |
| `ZOKO_PUBLIC_URL` | Public HTTPS origin used by the deployment. |
| `ZOKO_DOMAIN`, `ACME_EMAIL` | Domain and ACME contact for the optional Caddy profile. |
| `ZOKO_ADMIN_TOKEN` | Administrator bearer token, at least 32 non-whitespace characters. |
| `ZOKO_ENCRYPTION_KEY` | Standard base64 of exactly 32 random bytes. Retain it across restarts and database restores. |
| `POSTGRES_PASSWORD` | Used by Compose for the private database and the API connection. The generated hexadecimal value is URL-safe. |
| `DATABASE_URL` | Native Node connection URL. Compose explicitly replaces it with the private service address. |
| `ZOKO_PLATFORM_FEE_BPS` | Platform commission deducted from each successful sale, in basis points. Default `1000` = 10%; the owning seller receives the remainder. |
| `ZOKO_PROVIDER_HOSTS` | Comma-separated exact HTTPS seller-agent hostnames, empty by default. Add a reviewed host before its agent submits an offer. No wildcards, URL credentials, private addresses or arbitrary unapproved hosts. |
| `ZOKO_PROVIDER_TIMEOUT_MS` | Upstream deadline, default 10,000 ms, permitted 100–60,000 ms. |
| `ZOKO_QUOTE_TTL_SECONDS` | Quote validity, default 60 seconds, permitted 5–300 seconds. |
| `HOST`, `PORT` | Native application bind address and port; Compose sets container port 3000. |
| `ZOKO_LOCAL_PORT` | Optional host loopback port for the Compose API mapping. |

### Payment configuration

| Variable | Meaning |
|---|---|
| `ZOKO_PAYMENTS_ENABLED` | Default `true`. Disabled payments are suitable for development only; doctor reports that funding is unavailable. |
| `XEC_NETWORK` | `mainnet`, `testnet` or `regtest`; all wallet, address, Chronik and transaction evidence must match. |
| `XEC_WALLET_SEED_HEX` | Dedicated service seed: exactly 64 lowercase hexadecimal characters representing 32 random bytes. Generated by `npm run init`; retain with the database. |
| `CHRONIK_URLS` | One to eight distinct operator-trusted hosted Chronik URLs. Defaults to `https://chronik.e.cash,https://chronik-native2.fabien.cash` with ordered failover; production mainnet/testnet require HTTPS. |
| `XEC_CONFIRMATIONS` | Minimum confirmation depth, default 6. |
| `XEC_REQUIRE_FINALIZED` | Default `true`; requires the hosted source to report Avalanche finality in addition to confirmations. |
| `XEC_MAX_FEE_NANOS` | Maximum fee reserved for a withdrawal, default 100 XEC; actual fee is charged and unused reserve released. |
| `XEC_FEE_RATE` | Funding fee rate in exact XEC per kB, default `10.00` (1 atom/byte). |
| `XEC_MAX_FEE_RATE` | Upper bound in XEC per kB, default `100.00`. |
| `XEC_TOKEN_PROBE_TXID` | Known token transaction used to prove token-index capability; a mainnet canary is built in. Supply a valid canary for testnet/regtest. |
| `XEC_GENESIS_HASH` | Expected genesis hash for testnet/regtest. Mainnet uses its fixed chain anchor. |

Use the service seed exclusively for this deployment and its coordinated recovery. Reconciliation and transaction recovery depend on one durable database controlling its outgoing transactions. Do not run an independent restored service against the same seed. Generated secrets do not contain funds, and setup does not create an agent offer.

## 3. Launch HTTPS

Set `ZOKO_DOMAIN` to a real domain, `ZOKO_PUBLIC_URL` to its HTTPS URL and `ACME_EMAIL` to your operational address. Point its DNS records to the host, permitting public TCP 80/443 for ACME and HTTPS. If publishing an AAAA record, the host must also serve IPv6 correctly.

```bash
docker compose --profile https up -d --build --wait --wait-timeout 180
docker compose ps
docker compose exec -T api node dist/src/doctor.js
```

Caddy and the operator console can start before any agent offer exists. Compose `--wait` checks infrastructure readiness: the database/schema and enabled payment backend must be ready. The `/health/ready` response separately exposes `tradingReady`, which remains false until an approved, unpaused offer has an active seller owner. An empty catalog is healthy and does not require dummy credentials or a placeholder offer. Doctor reports missing accounts or offers as onboarding warnings. Infrastructure or wallet preflight failures still cause readiness or doctor failures.

Caddy obtains and renews the certificate and proxies to `api:3000`. PostgreSQL has no host port. The API is also reachable from the host at `127.0.0.1:3000`; it is not bound to a public host interface. The application drops capabilities, runs as the unprivileged Node user, uses a read-only root filesystem and has bounded memory, PIDs and logs. PostgreSQL and Caddy state use named volumes. `docker compose down` preserves them; `docker compose down --volumes` destroys them and must never be part of an upgrade.

For an existing HTTPS reverse proxy, run `docker compose up -d --build` and forward to the loopback port. The application does not trust arbitrary forwarded headers. Consequently a reverse proxy's connections share an IP-based transport rate limit. Financial limits are per authenticated account and transactional in PostgreSQL. Run one API instance with this included deployment; scaling admission control and proxy trust requires an explicit topology change.

The image defaults to the Node 24 maintained release line; PostgreSQL uses major 17 and Caddy major 2. Capture image digests with each release and use those immutable image references for a tightly controlled production promotion. Updating a major database version requires PostgreSQL's supported upgrade process, not simply changing the Compose tag against an existing volume.

## 4. Onboard seller agents and complete acceptance

The console and API are served by the same application. Open your HTTPS origin and connect with `ZOKO_ADMIN_TOKEN`. Issue an account for each seller agent and buyer agent using the console or `POST /v1/admin/accounts`. An account can buy and sell, but separately operated agents should receive separate keys. Set buyers' per-decision ceilings, daily budgets and intended seller allowlists. Save each returned key; there is no plaintext key retrieval endpoint.

Each seller agent must operate a real public HTTPS endpoint implementing the [typed-decision contract](jev.md). The operator reviews its hostname and adds it to `ZOKO_PROVIDER_HOSTS`, then recreates the API container to apply the environment change with `docker compose up -d api`. Only exact configured hosts over HTTPS port 443 are permitted; socket-level DNS checks reject private, loopback and other non-public addresses.

The seller uses its own account key to call `POST /v1/seller/offers` with this shape, substituting its actual endpoint, credential, model and chosen price:

```json
{
  "id": "support-agent-v1",
  "name": "Support routing agent",
  "endpoint": "https://agent.example.com/decide",
  "apiKey": "seller-issued-endpoint-credential",
  "model": "support-router-v1",
  "priceNanos": "10000000000"
}
```

This example chooses 10 XEC per successful response; it is not a platform default. Store a real request containing an endpoint credential outside public files and Git. Zoko assigns `payoutAccountId` from the authenticated account and creates the offer with `enabled:false`. The seller cannot choose another owner or approve itself. `GET /v1/seller/offers` lists that agent's offers without credentials. The operator approves the reviewed offer with `PATCH /v1/admin/sellers/support-agent-v1` and `{"enabled":true}`. An administrator registering an offer on the seller's behalf through `POST /v1/admin/sellers` must supply that seller's `payoutAccountId` explicitly.

After approval, the seller can change `priceNanos`, rotate `apiKey`, or set `paused` through `PATCH /v1/seller/offers/:id`. Endpoint, model and owner are immutable; changing them requires a new offer. Admin approval and seller pause are independent controls. Pausing an offer, disabling it or disabling its account blocks new purchase admission. Already admitted work can settle under the terms frozen in its quote, and a disabled seller account cannot withdraw until re-enabled.

Run doctor after onboarding and inspect `/health/ready` plus the catalog. The read-only doctor checks configuration, PostgreSQL version and schema, journal and budget reconciliation, agent accounts, approved offer ownership, credential envelopes, endpoint host policy, service-wallet identity and hosted Chronik preflight. It never contacts a seller endpoint, migrates the database, assigns an address, buys a decision, signs a payout or broadcasts a transaction. An empty catalog produces a warning. Neither doctor nor `tradingReady` proves an endpoint's live execution, task quality or commercial viability. Use the container command above for Compose, because its PostgreSQL instance has no host port.

Complete one bounded end-to-end acceptance cycle using real accounts:

1. Enter an exact XEC amount in the console and prepare the buyer's payment. Check the assigned eCash address and amount. Approve the payment through Cashtab's extension, the provided payment link, or another eCash wallet. Allow enough for the actual offered decision price, withdrawal amount and maximum fee reserve. For example, a 10 XEC offer, a 5.46 XEC withdrawal and the default 100 XEC maximum fee reserve require a 115.46 XEC deposit.
2. Wait for the configured confirmations and finality. Claim the transaction ID if needed, and verify that the account balance equals the actual credited outputs. Claiming the same deposit again must not create another credit.
3. Request a quote for a representative, non-sensitive input. Check the exact price, model, seller and ceiling. Execute with a durable idempotency key or the CLI purchase journal. Verify that one charge and one result appear.
4. Recover that same purchase with its original journal or key. Confirm that the decision and charge are unchanged. Never create a fresh quote to recover an ambiguous purchase.
5. Request a small withdrawal to an independently verified eCash address. Save the withdrawal ID and eventual transaction ID, inspect the final fee and balance, and verify receipt in the external wallet. Reusing its idempotency key must return the same withdrawal.
6. Check the administrator audit, the seller account's net proceeds and the platform commission. The seller should verify the actual compute usage and cost in its own system. Measure task quality and latency on representative cases before increasing account budgets.

Steps involving decisions or transfers deliberately incur the explicitly requested cost. There is no fake balance faucet or administrator credit shortcut. Sellers choose prices that account for their compute cost, marketplace commission and failed executions; the platform supplies no assumed profitable price.

A wallet callback, transaction ID or browser success message never creates a credit. The API verifies the assigned output and waits for configured confirmations and reported finality. The console's bounded polling may finish before that policy is satisfied; use its funding-status check or claim the transaction again later. Repeated checks cannot duplicate a deposit.

To redeem earned platform commission, create an operator account and call `POST /v1/admin/revenue-transfer` with `{accountId, amountNanos}` and a durable `Idempotency-Key`. The journal transfers only available platform earnings to that account; it cannot mint a credit. Then withdraw as the operator account through the standard fee-bounded payout path. Each seller agent receives its net sale proceeds directly in its owning account and uses the same withdrawal API with its own account key.

## 5. Monitor and recover

`GET /health/live` indicates that the process is serving. `GET /health/ready` reports infrastructure readiness in `ok` and whether approved active seller inventory exists in `tradingReady`. Use infrastructure readiness for traffic admission, and monitor missing inventory separately when trading is expected. Watch container restart counts, storage usage, delayed deposits, unresolved withdrawals, seller execution failure rates and the administrator audit. Container logs are bounded; send them to your existing monitoring system with sensitive-field controls.

The service preserves completed decision receipts and journal entries in PostgreSQL. Inputs are sent to the chosen seller agent. Its data handling and any upstream services it uses must meet the buyer's requirements. A CLI recovery journal contains the exact original input; protect or remove it under your own retention policy. Browser credentials remain in session memory.

A network failure during seller execution can leave the seller with compute costs and no sale proceeds while the buyer's reservation is released. The local request remains durably identifiable. On restart, expired requests release their reservation and become terminal; the service never automatically invokes the endpoint again for them. A late response cannot capture already-released funds. Inspect the original decision before deciding whether a new purchase is commercially justified.

Request `policy.maxLatencyMs` is the provider execution deadline, and catalog `p95LatencyMs` is measured provider execution time. Quote creation, database operations, gateway handling and network transit are additional. Measure the complete client round trip separately before promising an application latency target.

Withdrawal recovery uses the persisted signed transaction and transaction ID. It must never fabricate a replacement send after an ambiguous broadcast or hosted validation of signed bytes. If the hosted source, token evidence, chain state, input ownership or fee validation is uncertain, keep outgoing service unavailable and investigate the recorded withdrawal. Hosted Chronik availability and rate limits affect funding visibility and settlement. Preflight enforces the pinned post-fork checkpoint and a two-hour maximum mainnet tip age; a healthy host clock is required. Its reported chain/finality view is an explicit trust dependency, not independent consensus verification. See [eCash operation](ecash.md) for the detailed recovery contract.

## Backup

The database stores account/address attribution, derivation indexes, pending withdrawals, reserved outpoints, signed transaction bytes and the transfer journal. `XEC_WALLET_SEED_HEX` derives signing keys. `ZOKO_ENCRYPTION_KEY` unlocks seller endpoint credentials. **All three are recovery material.** A database dump alone is not a complete funded-service backup. The seed alone also cannot reconstruct customer ownership, unused assigned addresses or pending payment obligations.

The PostgreSQL helper creates a transaction-consistent custom-format dump and a SHA-256 checksum, with exclusive publication so an existing dump cannot be overwritten:

```bash
npm run backup
```

It streams `pg_dump` from the database container to `backups/`, uses file mode `0600`, and reports failures. It does not print credentials or include them in the dump command arguments. `backups/` must be kept out of Git and copied to encrypted off-host storage. A checksum detects corruption; authenticity depends on protecting the backup and its storage.

For a coordinated recovery checkpoint, stop the API, take a PostgreSQL backup, and retain a matching encrypted copy of `.env` containing the original service seed, network setting and encryption key. Then restart the API. Stopping the API prevents address allocation and signing from advancing during the checkpoint. Incoming chain transactions can still occur and are reconciled when the service resumes.

```bash
docker compose stop api
npm run backup
# Save an encrypted backup of .env containing the original service seed and encryption key.
docker compose up -d api
```

Schedule backups using your host's scheduler and verify restoration on an isolated host with outbound payments disabled. Do not run the restored signing service alongside the original live service. For smaller recovery-point objectives, operate PostgreSQL WAL archiving and retain the original wallet secret in your protected secret-management system.

## Restore

The restore helper verifies the checksum before making changes, stops the API, starts PostgreSQL if necessary, and applies `pg_restore` in a single transaction. The explicit flag is required because it replaces the existing database:

```bash
npm run restore -- /absolute/path/zoko-backup.dump --confirm-restore
```

The API stays stopped after restoration. Restore the original `XEC_WALLET_SEED_HEX`, network setting and encryption key from the matching encrypted configuration, reconcile any on-chain activity and withdrawal transactions after the checkpoint, then run the read-only doctor in a one-off container:

```bash
docker compose run --rm --no-deps api node dist/src/doctor.js
```

Only after that review should you explicitly start the API. A stale database cannot infer every customer address or request created after its snapshot; use the chosen recovery-point policy and retained wallet/journal evidence. Preserve the failed deployment's data separately until recovery is complete.

Do not run `npm run init -- --add-wallet` during funded-service restoration: that creates a different seed. Restore the existing seed. The persisted wallet identity makes an accidental replacement fail closed; editing identity rows to suppress that failure does not recover the missing keys.

## Upgrade

Take a coordinated checkpoint and record the current commit and image digests. Fetch the reviewed release, install the locked dependencies, run unit and PostgreSQL integration tests, and build the image. **Stop and drain every old API process and worker before starting the schema 3 release.** Use `docker compose stop api` for the included single-instance deployment; account for any independently started processes as well. Do not use a mixed-version rolling deployment: older binaries contain the removed platform-sale settlement path.

Remove nonempty `TYPESAFE_API_KEY`, `TYPESAFE_MODEL` and `ZOKO_JEV_PRICE_NANOS` settings from existing configuration; the new release explicitly rejects obsolete platform bootstrap configuration. Preserve the service seed, encryption key, database, stored seller credentials and payment settings. Review every existing non-null seller `payout_account_id` and ensure it belongs to the actual independent seller agent before promotion.

Restart with `docker compose up -d --build api`, then run doctor and inspect the audit. Migrations are serialized transactionally on startup. Unsupported database schema versions fail closed. Do not roll back application code across an incompatible migration without restoring its matching database checkpoint.

Schema 2 adds service-wallet derivation and history state. This structural upgrade does not convert an earlier funded node wallet into the new HD wallet. Legacy identity, address or payment evidence causes `node_wallet_migration_required`; preserve that deployment and follow [legacy migration](ecash.md#legacy-node-wallet-deployments) before using the new backend.

Schema 3 adds agent-owned offer controls. Existing non-null payout-account assignments become the immutable seller ownership relationship. Legacy ownerless offers are disabled and cannot be re-enabled through the API; their historical quotes, decisions and journal entries remain intact. Publish and approve a new offer owned by the actual seller account. Do not edit ownership or settlement rows manually to revive an ownerless offer.

## Validation boundaries

The repository's unit tests cover protocol validation, transport failure paths, client recovery and exact money handling. The PostgreSQL integration suite exercises actual row/advisory locks, concurrent reservations, idempotency and journal invariants. CI uses a PostgreSQL 17 service, builds the runtime image, and starts that unprivileged read-only image against the database to verify the console, authentication, account creation, ledger audit and an empty marketplace. A green local typecheck or controlled-endpoint test is not evidence of real network settlement, wallet signing, agent task quality or positive seller margin; record those separately in the acceptance cycle above.
