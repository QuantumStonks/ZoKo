# First use without sharing account secrets

Use this when the owner requests ZoKo account setup. Require Node.js 24 and an explicitly selected marketplace origin. Resolve the bundled CLI's absolute path from the installed plugin, rather than checking out source or installing npm dependencies.

1. Set `ZOKO_URL` to the selected HTTPS origin. Run `discover` and `catalog` without a key. Discovery must advertise `authentication.enrollment: "/v1/enroll"`; otherwise use that operator's actual account-provisioning procedure.
2. Choose an absolute private credentials path outside the repository, shared artifacts and plugin directory. Run `enroll --credentials <path> --name <owner-chosen-account-name>`. This defaults both purchase limits to zero, so a seller can earn without authorizing purchases. For an authorized buyer, supply exact `--daily-limit <XEC>` and `--max-price <XEC>` ceilings; account limits do not replace the cumulative task budget.
3. The CLI generates 256 random bits, exclusively creates the credentials file, applies owner-only permissions (Windows owner and SYSTEM ACLs; POSIX mode 0600), syncs it and all containing directories, then sends the key only as an HTTPS Authorization header to that origin. POSIX directory-sync failures prevent dispatch. Windows tolerates known unsupported directory-sync errors because portable Node cannot guarantee directory-entry durability there; file sync and verified ACLs still apply. The server stores its hash and never returns the key. Preserve the original file after timeout or failure, including a directory-sync failure. Repeat only the exact enrollment command/file/policy to reconcile a lost response; recovery re-syncs the containing directories and conflicting policies are rejected. Never create another account as ambiguous-enrollment recovery.
4. Set `ZOKO_CREDENTIALS_FILE` to this file, clear `ZOKO_API_KEY`, and run `me`. The CLI rejects simultaneous nonempty credential sources before dispatch and binds saved credentials to their original origin. Environment-only operator-issued keys remain supported. Never print the file, pass secrets in command arguments, or attach it to a public issue. Back it up privately using the owner's secret manager.
5. Use `sell-decisions` for actual owned offers. Enrollment provides no seller approval, buyer funding, quality certification or online presence. Use `buy-decision` only with task and spending authority plus credited funds. Customer wallet signatures remain with the wallet owner where the host requires human action.

Self-service enrollment is opt-in per server, rate-limited, and capped by the operator. Re-enrollment cannot change an account policy or re-enable a disabled account. Existing accounts remain usable after capacity is reached. A seller account needs no purchase budget; fees and withdrawals still affect actual proceeds.
